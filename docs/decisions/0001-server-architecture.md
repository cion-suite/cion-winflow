# 0001. Веб-архитектура cion-reader

- **Статус:** принято
- **Дата:** 2026-11-24
- **План:** [../planned-now.md](../planned-now.md)

## Контекст

cion-reader задуман как закрытый агрегатор манги, аниме и книг для себя и небольшого круга читателей. Нужны профили, авторизация, общая библиотека, прогресс и несколько источников у одного тайтла. Исходный код — десктопное приложение на Tauri с React-фронтендом.

Ограничения:

- пользователей мало (десятки), публичной регистрации нет;
- контент чужой: хранить его целиком нельзя и не нужно;
- SEO не нужен — сайт закрыт авторизацией;
- владелец изучает Rust, поэтому сервер на Rust предпочтителен;
- развёртывание — один VPS.

## Решение

1. **SPA на React + сервер на Rust (axum).** Фронтенд переезжает из Tauri почти без изменений; `src/api/client.ts` меняет `invoke` на `fetch`. Слои `app/shell/pages/api/ui/lib` и ESLint-границы сохраняются.
2. **SQLite + sqlx.** Один сервер, десятки пользователей; WAL и индексы покрывают нагрузку. Миграции — sqlx. Переезд на Postgres — только при появлении нескольких инстансов или реальной конкуренции записи.
3. **Тонкое зеркало контента.** В БД — нормализованные метаданные (тайтлы, источники, главы, страницы); изображения кэшируются на диске; видео не хранится. Источники опрашиваются адаптерами, клиент никогда не получает чужие URL.
4. **Канонический тайтл + N источников.** `titles` ← `source_entries`; пользователь видит одну запись в библиотеке. Связывание на первом этапе ручное.
5. **Закрытый доступ.** Регистрация по инвайтам, Argon2id, opaque-сессии в БД, HttpOnly-cookie, проверка `Origin` на мутациях.
6. **Один origin.** В dev — Vite с прокси `/api`, в проде — Caddy и axum на одном домене. CORS не нужен.
7. **Статика отдельно от бинарника.** `dist/` отдаётся `ServeDir` или Caddy; `rust-embed` не используется, чтобы правка UI не требовала пересборки сервера.

## Последствия

- Один репозиторий и один origin: фронтенд и бэкенд — два процесса только в разработке. В проде обновление `dist/` не требует пересборки или перезапуска сервера.
- Два процесса в разработке: Vite (HMR) и axum; правки фронтенда не пересобирают Rust.
- Появляется слой адаптеров источников — самая изменчивая часть; его тестируют на HTML/JSON-фикстурах.
- Нужны прокси изображений с кэшем и защитой от SSRF, фоновые задачи обновления и эвикшена.
- Нужны миграции БД, резервное копирование и проверка восстановления.
- CSP и заголовки безопасности задаются сервером; инлайновый скрипт темы из `index.html` придётся вынести или разрешить по хешу.
- Видео встраивается; HLS-прокси — отдельное решение при необходимости.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Next.js / Node SSR | второй язык и runtime на сервере, теряется смысл Rust-бэкенда; SSR не нужен закрытому приложению |
| Leptos / Dioxus / Yew (SSR на Rust) | пришлось бы выбросить React, shadcn, TanStack и экосистему; выше порог входа |
| Живой прокси источников | медленно, хрупко, каждый запрос зависит от чужого сайта |
| Полное зеркало контента | диски и трафик, превращение в файлохранилище; не нужно для закрытого круга |
| Отдельный фронтенд на CDN и API на поддомене | удобнее для независимых деплоев, но добавляет CORS и вторую точку деплоя; для одного сервера лишнее |
| Postgres с первого дня | лишняя инфраструктура для десятков пользователей; sqlx позволяет перейти позже |

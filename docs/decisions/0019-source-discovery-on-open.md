# 0019. Поиск недостающих источников при открытии тайтла

## Контекст

Решение 0011 привязывает копии тайтла только в момент добавления. Тайтл,
импортированный раньше (или добавленный, когда второй источник был выключен),
остаётся с одним источником: пользователь не видит главы, которых на нём нет,
хотя копия уже существует на другом включённом источнике. Повторно добавлять
тайтл ради привязки неудобно, а ручной привязки в UI нет.

Фоновый поиск при каждой синхронизации 0011 отклонял: он множит запросы и
может подмешать чужой тайтл. Нужен поиск, который не повторяется на каждом
рендере и не превращается в массовый обход библиотеки.

## Решение

1. **Поиск при открытии, а не при синхронизации всех тайтлов.** `sync_title`
   вызывает `source_discovery` до TTL-раннего выхода. Discovery ищет тайтл на
   включённых источниках того же языка, которых ещё нет в привязке, и
   импортирует точные совпадения по основному или альтернативным названиям
   (первая страница выдачи, до пяти запросов на источник). Массового обхода
   после импорта закладок нет: это тысячи поисков, отдельная будущая задача.
2. **Per-user кэш результатов.** `title_source_checks (title_id, source_id,
   user_id)` хранит `checked_at`, `status` (`found|not_found|auth_required|
   error`) и текст ошибки. `not_found` живёт 24 часа, `auth_required` и
   `error` — час. Открытие страницы в пределах TTL не ходит в сеть. Сохранение
   или удаление учётки пользователя удаляет его строки для источника: после
   подключения аккаунта поиск повторяется.
3. **Ошибка поиска — не «тайтла нет».** Успешный поиск без совпадения —
   `not_found`. 401 без учётки и неоднозначный 404 Remanga (18+ тайтл) —
   `auth_required`; прочие ошибки — `error`. Поэтому скрытый тайтл не
   кэшируется как окончательное отсутствие на сутки.
4. **Общая блокировка на тайтл.** `discover::add` и открытие страницы берут
   одну per-title блокировку, иначе два запроса импортировали бы один и тот же
   `(title, source)` дважды. `add` берёт её через `try_lock`: если открытие уже
   ищет, добавление поиск пропускает, и привязку доделает страница.
5. **Бюджет.** За одно открытие проверяется не больше трёх источников и шести
   поисковых запросов на источник, плюс общий таймаут. Остальные кандидаты
   пропускаются и попадают в `discovery.skipped`.
6. **Ответ и инвалидация.** `sync` возвращает `sources_linked` и
   `discovery: { checked, skipped, errors }`. Фронтенд инвалидирует страницу,
   если `refreshed` **или** `sources_linked` непуст: привязка меняет выдачу
   даже когда главы привязанных источников ещё свежие. Auth-ошибка discovery
   не двигает `metadata_synced_at` и показывает подсказку со ссылкой на
   настройки.
7. **Учётка действующего пользователя.** Поиск и импорт идут с его учёткой;
   ошибка одного пользователя не пишется в глобальный
   `source_entries.last_error` и не блокирует поиск для другого.

## Следствия

- Синхронизация страницы может стать дольше, если есть непроверенные
  источники: один поиск на источник. Кэш, бюджет и лимит источников держат
  это под контролем.
- Решение 0011 «не искать при синхронизации» уточняется: поиск остаётся
  запрещённым как безлимитный фон, но разрешён как ленивый per-user discovery
  с TTL. См. поправку в 0011.
- `title_source_checks` — не привязка: строка `found` не означает, что
  источник привязан. Источник привязывается импортом (`source_entries`), а
  таблица лишь кэширует результат поиска.

## Альтернативы

- **Искать при каждом sync без кэша.** Отклонено: каждое открытие страницы
  ходило бы во все источники, а отрицательный результат повторялся бы
  бесконечно.
- **Массовый обход всей библиотеки после импорта закладок.** Отклонено:
  тысячи поисков на одном импорте. Ленивый поиск при открытии даёт тот же
  эффект по мере чтения.
- **Отдельный HTTP-маршрут и polling.** Отклонено: страница уже вызывает
  `sync`; discovery укладывается в тот же ответ, а бюджет и таймаут не дают
  запросу висеть.

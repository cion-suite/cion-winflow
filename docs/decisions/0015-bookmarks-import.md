# 0015. Импорт закладок из JSON-экспорта Remanga

Дата: 2026-11-27
Статус: принято

## Контекст

Нужно перенести личную библиотеку и прогресс чтения с Remanga/ExManga в
cion-reader. Экспорт — JSON с двумя необязательными массивами `exmanga` и
`remanga`; элемент хранит числовой `type` статуса, `progress` (сколько глав
прочитано), `name`, `dir` и служебные поля. У ExManga свои числовые id
статусов (`50120392…50120398`), у Remanga — стандартные `1…7`; кастомные
статусы лежат вне этих диапазонов (например `34956`).

Файл может содержать сотни записей (у автора — 812), а импорт одного тайтла
ходит в сеть за метаданными, главами и обложками. Синхронный HTTP-запрос на
весь файл не подходит: он идёт минуты и обрывается прокси/браузером.

## Решение

- **Личный импорт.** Импорт запускает владелец библиотеки; сейчас это
  вкладка «Импорт/Экспорт» в `/settings` (перенос из профиля — решение
  0016). Роль admin не нужна: данные личные, как аватар.
- **Фоновое задание в памяти процесса.** `POST /api/me/import/bookmarks`
  (multipart `file`) только разбирает JSON, создаёт закладки для кастомных
  статусов и запускает `tokio`-задачу. `GET /api/me/import/bookmarks`
  отдаёт последнее задание пользователя; пока оно `running`, страница
  настроек опрашивает его каждые 1.5 с. Одно активное задание на
  пользователя (409 `import_in_progress`). Завершённые задания живут
  сутки.
- **Разбор статусов по позиции в блоке.** Сначала проверяется стандартный
  диапазон Remanga `1…7`. Затем в файле ищется непрерывный блок из семи
  значений вне этого диапазона; его значения по возрастанию дают
  `in_progress, planned, completed, dropped, on_hold, not_interested,
  favorite`. Всё остальное — кастомный статус.
- **Своя закладка на кастомный статус.** Для первого кастомного id
  создаётся закладка `new1`, для следующего — `new2` и т.д. Привязка
  хранится в `library_tabs.source_ref` (миграция 0013), поэтому повторный
  импорт находит закладку даже после переименования. Если лимит в три
  закладки исчерпан, запись получает встроенный fallback-статус
  (`in_progress` при `progress > 0`, иначе `planned`).
- **Слияние двух экспортов.** Внутри одного массива записи склеиваются по
  `dir`. Между `exmanga` и `remanga` — сначала по `dir`, затем по
  уникальному нормализованному названию (как просил перенос). Из пары
  остаётся запись с большим `progress`. Одинаковые названия разных
  произведений внутри одного массива не сливаются: у них разные `dir`, а
  пара по имени неоднозначна.
- **Прогресс — первые N доступных глав.** `progress` означает число
  прочитанных глав. Сервер берёт канонический список глав страницы тайтла,
  убирает `locked`/`missing`, сортирует как UI и отмечает первые
  `min(progress, available)` глав в `chapter_reads`. Если `progress` больше
  числа доступных глав, отмечаются все. Позиция `progress` ставится на
  последнюю отмеченную главу (как выбрал пользователь); страница/тип
  контента не задаются — читалка откроет главу с начала. Существующие
  отметки не снимаются.
- **Существующая запись библиотеки.** Статус и своя закладка перезаписываются
  из файла, только если текущий `chapter_reads` меньше `progress` из файла;
  иначе ручной статус сохраняется. Новые записи создаются сразу с нужным
  статусом.
- **Поиск по названию при устаревшем `dir`.** Сначала импорт по `dir`.
  Если источник отвечает 404/невалидным id, выполняется поиск Remanga по
  `name` и берётся только точное нормализованное совпадение основного или
  альтернативного названия. Остальные ошибки попадают в отчёт.
- **Ограниченная параллельность.** Внутри задания не больше трёх
  параллельных тайтлов; при `429 source_rate_limited` задание ждёт
  `Retry-After` (до 120 с) и повторяет запрос один раз. Файл — до 3 МиБ и
  5000 записей.

## Последствия

- `GET /api/me/import/bookmarks` возвращает `{ job: null | { state,
  total, processed, succeeded, failed, titles_imported, library_created,
  library_updated, read_marked, errors, … } }`. Ошибки обрезаны до 200
  записей с флагом `errors_truncated`.
- После завершения фронтенд инвалидирует `profile`, `library`,
  `library-tabs`, `title`, `chapter-content` и `progress`: импорт меняет
  карточки, статусы, отметки и точку продолжения.
- Задание живёт в памяти: перезапуск сервера прерывает импорт. Повторный
  запуск безопасен — импорт идемпотентен по `(source_id, external_id)` и
  `chapter_reads`, а закладки находятся по `source_ref`.
- Прогресс считается по видимым главам: если на старом сайте глава была
  прочитана, а в текущем источнике она `locked`/`missing`, она не
  отмечается и не сдвигает позицию.

## Альтернативы

- **Синхронный импорт в HTTP-запросе.** Отклонено: 800 тайтлов — это
  тысячи сетевых запросов, запрос неизбежно оборвётся.
- **CLI-утилита вместо UI.** Отклонено: пользователь просил кнопку в
  интерфейсе, а сервер уже умеет отдавать статику и API.
- **Импортировать только библиотеку без глав.** Отклонено: тогда
  `read_count` и «Продолжить» остались бы пустыми, а смысл переноса —
  именно прогресс.
- **Записывать `progress` через `PUT /api/progress`.** Отклонено: сервис
  требует известный `content_kind` и сходил бы в сеть за каждой главой;
  импорт пишет канонический ключ напрямую, без позиции внутри главы.
- **Кастомные статусы в одну закладку.** Отклонено: разные внешние статусы
  должны оставаться различимыми; `source_ref` даёт стабильную привязку.

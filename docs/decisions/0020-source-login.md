# 0020. Вход в Remanga по логину и паролю

Дата: 2026-11-28
Статус: принято (фаза 5а)

## Контекст

Учётки источников уже серверные и общие для устройств (0017), но получить
их на телефоне было нечем: браузер не может прочитать ответ Remanga из-за
CORS, а ручная вставка Bearer/Cookie требует найти токен в devtools.
Расширение-компаньон для телефона недоступно, OAuth-клиент Remanga не
регистрирует. Спайк B подтвердил, что v1-логин возвращает долгоживущий
непрозрачный токен, а upgrade/refresh для базового сценария не нужны.

## Решение

- **Логин делает сервер.** `POST /api/me/source-credentials/{code}/login`
  (`{ login, password }`) вызывает v1 `POST /api/users/login/` и сохраняет
  `content.access_token` как Bearer-учётку в `user_source_credentials`.
  Пароль живёт в `SecretString`/`Zeroizing`, не хранится, не логируется и не
  возвращается API.
- **Нужны оба флага.** Источник объявляет `Capability::Login` рядом с `Auth`;
  форма входа показывается только при наличии обоих. Ручная вставка
  Bearer/Cookie остаётся серверным API (`PUT`), из UI убрана. Fixture
  реализует логин для dispatch-тестов, но не рекламирует флаги, поэтому в
  настройках не появляется.
- **Проверка без пароля.** `POST /api/me/source-credentials/{code}/verify`
  не требует пароля: он проверяет уже сохранённый токен запросом Remanga
  `users/current`, обновляет `last_verified_at` или пишет
  `last_error='auth_invalid'`. Так статус в настройках можно обновить, не
  вводя учётку заново.
- **Сырой ответ только для логина.** Общий `send_text` скрывает тело 4xx;
  отдельный `post_json_raw` возвращает статус, `content-type` и тело с теми
  же лимитами, ретраями и circuit breaker. Это позволяет отличить 400
  `{msg}` (неверная пара) от 403 HTML (DDoS-Guard/Cloudflare), не ослабляя
  остальные запросы.
- **Ошибки не раскрывают детали.** 400/401 → `source_login_failed`,
  2FA → `source_login_2fa_required` (методы в сообщении), 403 HTML →
  `source_blocked`, 404 → `source_not_found`, сеть/5xx → существующие
  502/503. HTTP 401 наружу не отдаётся никогда.
- **Проверка при входе.** Успешный логин ставит `last_verified_at`, сбрасывает
  `titles.metadata_synced_at` и per-user кэш `title_source_checks` — тот же
  путь, что у ручного сохранения учётки.
- **Перебор ограничен.** IP-лимит как у входа в приложение плюс счётчик на
  пользователя: 5 попыток за 10 минут, затем 429 с `Retry-After`. Счётчик
  живёт в памяти процесса и сбрасывается удачным входом.

## Последствия

- Телефон входит по паре логин/пароль; токен после этого общий для всех
  устройств, отдельного хранения на клиенте нет.
- 2FA-аккаунты пока не входят: это фаза 5б. Refresh-пара не нужна, пока
  v1-токен не отзывается (5в).
- Пароль в запросе неизбежно существует в памяти процесса и в теле запроса
  к Remanga; `Zeroizing` сокращает время жизни буфера, но не делает его
  недоступным отладчику.
- DDoS-Guard может отклонить логин с датацентрового IP — это репутация IP,
  а не ошибка пары; лечится egress-прокси (фаза 7).

## Альтернативы

- **Перенос `auth:token` букмарклетом/расширением.** Остаётся запасным
  путём, но требует ручного шага и не решает первичное подключение на
  телефоне так же просто, как форма.
- **OAuth2.** Провайдер есть, публичной регистрации клиента нет.
- **Клиентский фетчинг.** CORS не даёт SPA прочитать ответ Remanga;
  юзерскрипт-мост — отдельная тяжёлая фаза.
- **Хранить пароль и повторять логин при 401.** Отклонено: пароль — более
  чувствительный секрет, чем токен, и его утечка не отзывается сменой
  токена.

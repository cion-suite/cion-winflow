# 0002. Гетерогенные источники: контракт, возможности и нормализация

- **Статус:** принято
- **Дата:** 2026-11-24
- **План:** [../planned-now.md](../planned-now.md)
- **Связано:** [0001-server-architecture.md](0001-server-architecture.md), [0003-source-selection.md](0003-source-selection.md)

## Контекст

Первая версия плана (§7) предполагала одну форму источника: `search → title → chapters(number: f32) → pages`. Реальные источники так не устроены:

- типы произведений разные — манга, аниме, книги; один сайт может отдавать несколько типов;
- названия, альтернативные названия, авторы, жанры, статус, год и обложки приходят в разных формах и не всегда полными;
- главы нумеруются с 0 или 1, бывают дробными, диапазонами «1-2», томами, спецвыпусками без номера, несколькими группами перевода на одну главу;
- контент — страницы-картинки, iframe-плеер, HLS или текст книги; часть источников требует подписанные URL или DMR-обработку;
- пагинация — номер страницы, offset или курсор; фильтры у каждого сайта свои;
- авторизация — куки, токены, Cloudflare; лимиты и ошибки тоже различаются.

Из этого следует, что «источник» — не набор полей, а отдельная подсистема. Общим может быть только узкий контракт, а разбор сайта, нумерация, конфиг и тесты живут внутри адаптера.

Для сравнения изучен Suwayomi-Server: он исполняет Kotlin/Android-расширения (`Source`/`CatalogueSource`, DTO `SManga`/`SChapter`/`Page`, магазин расширений). Оттуда взяты идеи узкого DTO, опциональных возможностей и отдельного жизненного цикла источника; динамическая загрузка расширений не переносится.

## Решение

1. **Компилируемые адаптеры и enum dispatch.** `enum SourceKind` с исчерпывающим `match` — единственная точка вызова. Трейт `Source` и `dyn` не используются: `async fn` в трейте не dyn-совместим, набор источников фиксирован, а enum заставляет компилятор проверять полноту при добавлении варианта. Динамические плагины (WASM/APK) не вводятся: для закрытого проекта достаточно пересборки.

2. **Дескриптор источника — данные.** `SourceDescriptor` объявляет `code`, `name`, `version`, `kinds`, `default_kind`, `capabilities`, схемы `config` и `filters`. Возможности — флаги (`Search`, `Chapters`, `Images`, `VideoEmbed`, `Text`, `Volumes`, `AltNames`, `SearchFilters`, `AuthCookie`, `SignedUrls`), а не набор трейтов. Обработчик проверяет флаг до вызова адаптера и не угадывает поведение по исключениям.

3. **Честные DTO.** Неизвестное поле — `Option`, а не пустая строка или ноль. `SourceTitle` несёт `kind`, альтернативные названия, авторов, жанры, статус, год и `cover_ref`; `SourceChapter` — `external_id`, `chapter_key`, `number_text`, `number_milli`, том, вид главы, `content_kind`, группу перевода, язык и признак блокировки. `SourceContent` — размеченный enum `Images | Video | Text`; тело книги не инлайнится в ответ.

4. **Тип контента хранится на главе.** `chapters.content_kind` — единственный источник истины для `pages`, `embed_url` и текста. Он может быть NULL, пока источник не отдал тип в списке глав: тогда фактический вариант определяется при первом `content()` и записывается. Если тип известен и расходится с ответом — 502; `GET /api/chapters/{id}/text` для не-текстовой главы — 409.

5. **Ключ главы строит адаптер.** Номер нельзя хранить как `f32`. В БД лежат `number_text` (как у источника), `number_milli` (только сортировка), `ordinal_site` (порядок выдачи), `chapter_key` (NOT NULL). Формат: с томом — `v{vol}:c{number_text}`, без тома — `c{number_text}`; для любого вида кроме normal — `{vol_seg}{kind}:c{...}`; без номера — `{vol_seg}{kind}:x:h{sha256(external_id)[..16]}`. Ключ фиксируется при первом импорте и не меняется при refresh; безномерные главы не склеиваются между источниками и группами с разными `external_id` — это ограничение, а не баг.

6. **Прогресс — только по каноническому `chapter_key`.** `progress` и `chapter_reads` не хранят `chapter_id` или номер и живут в SQLite. API принимает `chapter_key`, сервер резолвит alias → canonical и берёт `content_kind` выбранного варианта, затем проверяет, что поле позиции (`page`/`seconds`/`scroll`) соответствует типу контента. Несопоставленные ключи разных источников связывает администратор; автоматических эвристик нет.

7. **`external_id` — непрозрачная строка.** UTF-8, непустая, ≤ 256, без control-символов, `://` и `..`. Ограничение ASCII недопустимо: у источников бывают кириллические и percent-encoded id; URL-кодирует адаптер.

8. **Конфиг источника типизирован и версионирован.** `sources.config_json` содержит общий `CommonConfig` и поля адаптера; `sources.base_url` — отдельная колонка, а не поле конфига; `sources.descriptor_version` фиксирует версию адаптера, под которую валидировался конфиг, `config_error` — причину отключения. Битый конфиг отключает только свой источник. Секреты маскируются в API и не логируются; хранение в SQLite для self-host допустимо.

9. **Деградация вместо 500.** Отключённый или удалённый источник даёт `source_disabled` (503), а записи и библиотека остаются читаемыми. Если основной источник выключен, выбирается первый включённый `source_entry`; `is_primary` автоматически не переписывается.

10. **Контрактные тесты и probe.** Каждый адаптер обязан пройти `contract_suite`: дескриптор, фикстуры, уникальность `external_id`, совпадение известного `content_kind` (NULL допустим), уникальность ключа с учётом групп, стабильность ключа при повторном импорте, формат и лимит текста, сборку `config.example.json`, golden JSON. До написания адаптера кандидат проверяется `POST /api/sources/{code}/probe` (ok/auth/cloudflare/parse).

11. **Манга и аниме одного произведения — разные тайтлы.** Связь между ними (`title_relations`) появится позже, если понадобится. Один тайтл не может иметь записи разных `kind`: один `progress` не способен описать и страницу, и секунды.

## Последствия

- Добавление источника — новый модуль `sources/<code>/` с дескриптором, парсерами, фикстурами и конфигом; остальной код не меняется.
- Схема БД создаётся сразу в итоговой форме (включая `chapter_texts` и `chapter_aliases`), чтобы фазы 4–6 не делали `ALTER`; `jobs` появляется в фазе 7.
- Каталог, библиотека и API не содержат условий вида «если источник X».
- Ошибки источников типизированы и видны в UI разными сообщениями; один упавший источник не ломает выдачу.
- Цена: больше полей и проверок в DTO; адаптер обязан сам решать, что считать ключом главы. Это осознанно: скрывать различия источников дороже.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Один «толстый» `Source` trait с async-методами | не dyn-совместим, фиксированный набор источников не требует объектов; enum проще и даёт проверку полноты |
| Три enum-контракта по типам произведения (`MangaSource`/`AnimeSource`/`BookSource`) | на каждый метод — тройное делегирование; мультитиповый сайт требует нескольких карт; переписывает §7 целиком ради малого выигрыша |
| Динамические расширения (WASM, APK, внешние процессы) | сложность загрузки, версионирования и безопасности несопоставима с закрытым проектом на несколько источников; не даёт учебной ценности для текущих фаз |
| Универсальный scraping-DSL (селекторы в конфиге) | не покрывает API, видео, авторизацию и особые случаи; DSL по одному примеру — переусложнение. Вернуться, когда появится третий простой HTML-источник с той же формой |
| Хранить номер главы как `f32` | разная база, тома, диапазоны и спецвыпуски; сравнение float даёт ложные совпадения |
| Автоматически склеивать главы и тайтлы между источниками | эвристика ошибается на нумерации и переводах; ручное связывание предсказуемее |
| Хранить полный текст книг в БД | противоречит решению 0001 «тонкое зеркало»; текст — кэш с TTL и лимитом |
| Секреты только в env/файле | невозможно настроить авторизуемый источник из админки; для self-host достаточно маскирования и запрета логов |

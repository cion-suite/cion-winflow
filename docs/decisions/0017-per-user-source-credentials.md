# 0017. Учётки источников на пользователя

Дата: 2026-11-27
Статус: принято (фазы 1–2)

## Контекст

Remanga скрывает часть тайтлов (18+, закрытые) от гостей: без входа она
отдаёт 404 или пустую выдачу. Инсталляция многопользовательская, поэтому
общая cookie или токен на сервере означали бы, что чтение одного человека
работает под аккаунтом другого. Браузер не может сам прочитать
HttpOnly-cookie чужого origin, а хранить токен в `localStorage` фронтенда
значит отдать его любому XSS на странице приложения.

Первый импорт закладок показал три класса проблем: 18+ тайтлы не
импортируются без входа, импорт теряет прогресс больше доступных глав,
источники привязываются только при добавлении через поиск. Эта фаза решает
первую часть — хранение учёток; использование в запросах, прогресс и
ленивая автопривязка идут отдельными фазами.

## Решение

- **Учётки per-user.** Таблица `user_source_credentials` с ключом
  `(user_id, source_id)`. Один пользователь не видит и не может удалить
  учётку другого: все запросы берут `user_id` из сессии, а не из тела.
- **Шифрование AEAD.** Плейнтекст — JSON `{"bearer":"...","cookie":"..."}`
  — шифруется ChaCha20-Poly1305. Случайный 12-байтный nonce хранится рядом
  с шифротекстом; AAD `user_id:source_id:key_version` не даёт перенести
  строку другому пользователю или источнику. Плейнтекст оборачивается в
  `Zeroizing`/`SecretString` и не логируется.
- **Ключ — только в env.** `SOURCE_CREDENTIALS_KEY` — 32 байта base64
  (`openssl rand -base64 32`), пример — в `.env.example`. Формат
  проверяется при старте: битый ключ — отказ запуска. Если ключ не задан,
  приложение работает, но маршруты `/api/me/source-credentials*` отвечают
  503 `credentials_unavailable`. Потеря или замена ключа делает сохранённые
  учётки нечитаемыми; их нужно подключить заново.
- **Bearer и Cookie необязательны.** Отправляется то, что заполнено
  (использование — следующая фаза). Пустая строка и `null` очищают поле;
  `PUT` заменяет payload целиком, а не мержит его. Сохранение без единого
  поля отклоняется — для очистки есть `DELETE`.
- **API не возвращает секретов.** `GET /api/me/source-credentials` отдаёт
  по каждому источнику с `Capability::Auth`: `code`, `name`, `configured`,
  `updated_at`, `last_verified_at`, `last_error`. Источники без учётки тоже
  попадают в ответ с `configured=false`, чтобы UI показал форму до первого
  сохранения. `PUT`/`DELETE` — на `/api/me/source-credentials/{code}`,
  под rate limit и обычной проверкой Origin.
- **Право на учётку объявляет дескриптор.** Новый `Capability::Auth`
  (`auth`) стоит у Remanga; UI показывает только такие источники. Старый
  `AuthCookie` не трогаем: он про глобальный конфиг источника, а не про
  пользователя.
- **Сброс TTL синхронизации.** Сохранение и удаление учётки обнуляют
  `titles.metadata_synced_at` у тайтлов, где источник привязан. Иначе
  `POST /api/titles/{id}/sync` до 10 минут возвращал бы `refreshed=false`, и
  подключивший аккаунт пользователь не увидел бы изменений.
- **Ручная вставка — временный путь.** До появления расширения-компаньона
  пользователь вставляет Bearer/Cookie в настройках. Целевой вход по
  кнопке (расширение забирает cookie и `Authorization` после ручного входа
  на remanga.org и передаёт их по одноразовому коду) — отдельная фаза.

## Использование в запросах (фаза 2)

- Учётка резолвится по `(user_id, source_id)` перед запросом. Remanga
  получает `Authorization`/`Cookie` в `search`, `title`, `chapters` и
  `content`. Заголовки добавляются только на хосты источника (`base_url` и
  `site_url`), но не на `*.reimg.org` и другие CDN картинок: сессионная
  cookie не должна уходить третьей стороне. Если сохранённое значение уже
  содержит схему `Bearer`, второй раз она не добавляется.
- Ошибки различаются по наличию учётки. 401 без учётки → 403
  `source_auth_not_configured`; 401 с учёткой → 502 `source_auth_invalid`;
  404 Remanga без учётки неоднозначен (18+ тайтл скрыт) → 403
  `source_auth_maybe_required`; с учёткой тот же 404 — окончательный
  `source_not_found`; 403 сайта → 502 `source_blocked`. HTTP 401 наружу не
  отдаётся никогда, иначе фронтенд принял бы ответ источника за истёкшую
  сессию. Fallback по названию не глотает auth-ошибки.
- `source_entries.auth_required` и `chapters.auth_required` (0015)
  запоминают, что источник/глава требует вход. Первое открытие обычной главы
  идёт без учётки, при 401/404 повторяется с ней; успех с учёткой ставит
  `chapters.auth_required=1` и обновляет `last_verified_at`, успех без неё
  сбрасывает флаг. Помеченная глава отдаётся из кэша только пользователю с
  учёткой, проверенной менее 24 часов назад.
- Персональная auth-ошибка не меняет глобальную доступность: не пишется в
  `source_entries.last_error`, не ставит `locked` и не сдвигает
  `titles.metadata_synced_at`; ошибки sync/discovery/импорта возвращаются
  рядом с машинным `error_code`. UI показывает подсказку и ссылку на
  `/settings`, карточка «Источники» — «подключить аккаунт».
- Картинки помеченной главы кэшируются в пространстве `user:{id}`;
  публичные — в общем кэше. 401/403/410 при скачивании картинки не ставят
  глобальный `locked`.

## Последствия

- В `/settings` появилась третья вкладка «Источники»: статус, поля
  Bearer/Cookie (`type="password"`), «Сохранить», «Очистить». Кнопка
  «Проверить» пока disabled: у Remanga нет стабильного лёгкого endpoint,
  поэтому учётка проверяется первым реальным запросом и обновляет
  `last_verified_at`.
- Появились коды ошибок `credentials_unavailable` (503) и
  `source_credentials_invalid` (400); оба переводятся в UI.
- Фронтенд после сохранения/удаления инвалидирует `source-credentials`,
  `title`, `library` и `chapter-content`.
- Секреты не попадают в БД, логи и ответы API; это проверяет
  `server/tests/source_credentials.rs` (шифротекст, отсутствие плейнтекста в
  ответе и в строке БД, изоляция пользователей, очистка, неверный ключ).
- Таблица `title_source_checks` появится в фазе ленивой автопривязки; тогда
  же сохранение/удаление учётки начнёт удалять и её строки.

## Альтернативы

- **Одна глобальная учётка на инсталляцию.** Отклонено: смешивает
  пользователей и раскрывает чужой аккаунт всем читателям.
- **Хранить токен в `localStorage` и подставлять на клиенте.** Отклонено:
  XSS получает токен, а сервер не может отличить пользователя от подделки.
- **Плейнтекст в БД.** Отклонено: копия БД или резервный бэкап раскрывает
  аккаунты; шифрование в приложении — минимальная гигиена.
- **Cookie общим конфигом источника.** Отклонено: конфиг общий для всех, а
  вход — личный; 18+ контент стал бы доступен всем без входа.
- **Расширение сразу.** Отклонено в этой фазе: нужен рабочий серверный
  контракт и UI, иначе расширению некуда передавать секрет. Ручная вставка
  даёт тот же результат и остаётся fallback после появления расширения.

## Поправка 2026-11-27 (после проверки Remanga)

- У Remanga токен лежит в cookie `auth:token`, которая **не HttpOnly**:
  SPA читает её через `document.cookie` и подставляет `Authorization`.
  HttpOnly только `auth:server-token`, который API для обычных запросов не
  использует. Поэтому посылка «браузер не может прочитать токен» для Remanga
  неверна, и расширение с `cookies`/`webRequest` не обязательно.
- Учётки уже серверные и общие для всех устройств: `user_source_credentials`
  с ключом `(user_id, source_id)`. Расширение нужно только для первичного
  получения учётки; телефон читает под ней без установок.
- Проверены альтернативы: серверный вход по логину/паролю, перенос
  `auth:token` букмарклетом/юзерскриптом, OAuth2 (провайдер есть, но нет
  публичной регистрации клиента), per-user egress-прокси и клиентский
  фетчинг. Каталог вариантов, цены, риски и спайки — в
  `docs/authorization.md`.
- Расширение остаётся опциональным десктопным удобством, а не обязательной
  фазой.

## Поправка 2026-11-28 (фаза 5а)

- Целевой путь получения учётки для телефона — серверный вход по логину и
  паролю: `POST /api/me/source-credentials/{code}/login` вызывает v1
  `POST /api/users/login/`, получает непрозрачный токен и сохраняет его как
  обычную Bearer-учётку. Пароль не пишется в БД, ответ или лог.
- Вход сразу ставит `last_verified_at`: источник только что подтвердил пару,
  поэтому помеченные главы доступны без ожидания первого запроса.
- 2FA пока не поддерживается: такому пользователю вход возвращает 409
  `source_login_2fa_required`; ввод кода — отдельная фаза 5б.
- Ручная вставка Bearer/Cookie остаётся fallback, а расширение и перенос
  `auth:token` — запасными путями (фазы 8–10), не обязательным этапом.

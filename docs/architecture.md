# Устройство фронтенда

Код `src/` разложен по слоям. Импорты между файлами `.ts` и `.tsx` проверяет `pnpm lint`. Имена файлов линтер не проверяет, это договорённость.

| Слой | Что лежит | Сейчас в приложении |
|---|---|---|
| `app/` | запуск: `index.tsx`, провайдеры, маршрутизатор, глобальные стили | `AppProvider.tsx`, `AppRouter.tsx`, `styles/index.css` |
| `shell/` | оболочка окна: то, что не принадлежит ни одному экрану | `layout/`, `navbar/` (шапка, язык, тема), `sidebar/` |
| `pages/<имя>/` | экраны, по папке на экран | `home/`, `network/`, `changelog/`, `settings/` |
| `api/` | связь с Rust | `client.ts`, `index.ts` (команд пока нет) |
| `ui/` | `shadcn/` и мелкие общие компоненты | `shadcn/`, `PageHeader.tsx` |
| `lib/` | утилиты, хуки и типы без UI | `utils.ts`, `settings.ts`, `i18n/` |

Файл `.ts` или `.tsx` вне этих папок — ошибка линтера (`boundaries/no-unknown-files`).

## Кто кого импортирует

| Слой | Может импортировать |
|---|---|
| `app` | `shell`, `pages`, `api`, `ui`, `lib` |
| `shell` | `api`, `ui`, `lib` |
| `pages` | `api`, `ui`, `lib` |
| `api` | `lib` |
| `ui` | `lib` |
| `lib` | ничего из этих слоёв |

Внутри своей папки импортировать можно всё. Снаружи `api` доступен только через `@/api` и `@/api/client`.

## Куда положить код

- Нужен одному экрану — в папку этого экрана.
- Компонент нужен нескольким экранам — в `ui/`, данные он получает пропсами.
- Хук или утилита нужны нескольким экранам — в `lib/`.
- Логика приложения — в команду Rust.

## Экраны и меню

Экран — `pages/<имя>/index.tsx`, рядом лежат его компоненты. Файл называется `index`, а компонент — по экрану (`export function HomePage`), импорт выглядит так: `@/pages/home`. Импортировать экран может только `app`, экраны друг друга не импортируют.

Пункты меню и их порядок — единая таблица `shell/sidebar/sections.ts`. Она же задаёт `SectionPath`, а роутер (`app/AppRouter.tsx`) требует экран для каждого пути кроме главной: забытый маршрут не скомпилируется. Главная — `index`-маршрут `/`, поэтому в таблице у неё путь `/`.

В сайдбаре две группы без заголовков: `main` (Главная, Сеть) и `footer` (Что нового, Настройки). Свернуть сайдбар можно кнопкой в шапке или `Ctrl+B`; состояние сохраняется в настройках.

## Настройки

`lib/settings.ts` хранит пары ключ-значение. Ключи: `locale` и `sidebarOpen`. В приложении Tauri они лежат в файле `settings.json` в данных приложения (`@tauri-apps/plugin-store`, разрешение `store:default`), в обычном браузере — в `localStorage` под ключом `cion-winflow:settings`.

Порядок запуска в `app/index.tsx` важен: `initSettings()` читает сохранённые значения, `initI18n()` берёт из них язык, и только потом приложение рендерится — иначе интерфейс мигал бы языком по умолчанию. Компоненты читают настройку через `useSetting(key)` и пишут через `settings.set(key, value)`.

## Язык интерфейса

Переводы — i18next и react-i18next. Все строки под пространством имён `common` в `lib/i18n/locales/en.ts` и `ru.ts`; состав языков — `resources.ts` (`SUPPORTED_LOCALES`, `DEFAULT_LOCALE`). В компонентах `useT()` возвращает функцию перевода, `useLocale()` — текущий язык.

Выбранный язык лежит в настройке `locale`; `initI18n()` подписан на её изменение и вызывает `i18n.changeLanguage`. Переключатель — `shell/navbar/LocaleMenu.tsx`. При первом запуске берётся язык системы, если он есть в `SUPPORTED_LOCALES`.

## Тема

Тема — это класс `dark` на `<html>`. Скрипт в `index.html` ставит его до первой отрисовки: берёт выбор из `localStorage` (ключ `theme`), а если выбора нет, то тему системы. `shell/navbar/ThemeToggle.tsx` переключает класс, сохраняет выбор и через Tauri меняет тему заголовка окна. Для этого в `capabilities/default.json` есть разрешение `core:window:allow-set-theme`.

## Страница «Что нового»

`pages/changelog/` импортирует `docs/versions/release.md` как текст (`?raw`) и разбирает разделы `### Версия vX.Y.Z` с буллетами (`release-notes.ts`). Отдельного запроса к бэкенду нет: страница всегда соответствует файлу на момент сборки.

## Связь с бэкендом

Вся логика живёт в командах Rust. `api/` не содержит логики, только имена команд и типы. Сейчас команд в приложении нет, поэтому `api/index.ts` пуст:

```
pages/<экран>/index.tsx → api/<область>.ts → api/client.ts → команда Rust
```

| Файл | За что отвечает |
|---|---|
| `api/client.ts` | `call<T>()`: единственное место с `invoke`, приводит любую ошибку к `Error` |
| `api/<область>.ts` | Хуки команд одной области: `useQuery` для чтения, `useMutation` для изменений |
| `api/index.ts` | Собирает области в объект `api` |

Страница получает от хука всё готовое. Хук на `useMutation` даёт `mutate`, `data` и `error`, хук на `useQuery` — `data`, `error` и `refetch`.

Новая команда — это всегда три шага:

1. В Rust написать функцию с `#[tauri::command]`.
2. Дописать её в `generate_handler![...]`.
3. Добавить хук в `api/<область>.ts`. Новую область подключить в `api/index.ts`.

Правила:

- **Все методы `api.*` — хуки**, имя начинается с `use`. Вызывай их только в начале компонента: `react-hooks/rules-of-hooks` не распознаёт `api.x.useY()` и не поймает такой вызов внутри `if`.
- **Вне компонента** импортируй `call` из `@/api/client`.
- **`invoke`** импортируется только в `api/client.ts`: обычный импорт в другом файле и импорт корневого пакета `@tauri-apps/api` линтер отклоняет. Динамический `import()` он не видит.
- **Ключ запроса** — `[имя команды, ...аргументы]`. Перечитывание данных после изменения настраивается в хуке через `onSuccess` и `invalidateQueries`, а страница об этом не знает. Опечатка в ключе не даёт ошибки: данные просто не перечитаются.
- **Типы** сверяются с Rust вручную. `call<T>` ничего не проверяет во время работы, а опечатка в имени команды всплывёт только при вызове.
- **Ошибки.** `invoke` отклоняется тем, что выдал `Serialize` ошибки в Rust: строкой или объектом. `call` приводит их к `Error`, исходное значение остаётся в `error.cause`.
- **`QueryClient`** в `AppProvider.tsx` настроен под локальные команды: `networkMode: "always"`, без повторов и без перечитывания при фокусе окна.
